# Environment Variables

Consolidated reference for all environment controls. The primary config file on macOS and Linux is `/etc/edgecoder/edgecoder.env`. See [`scripts/macos/payload/etc/edgecoder/edgecoder.env.example`](https://github.com/codyrs82/Edgecoder/blob/main/scripts/macos/payload/etc/edgecoder/edgecoder.env.example) for a fully-annotated template.

## Runtime mode

`NODE_ENV` (default `development`): `production` turns on the production-only checks listed under [Startup validation](#startup-validation-15).

| Variable | Values | Description |
|---|---|---|
| `EDGE_RUNTIME_MODE` | `all-in-one` (default) \| `agent` \| `worker` \| `coordinator` \| `portal` \| `control-plane` \| `inference` \| `ide-provider` \| `install` | Selects which service the `edgecoder` launcher runs. Any other value stops the launcher with the list of roles. |
| `HOST` | `127.0.0.1` | Listen address for all HTTP services; set `0.0.0.0` in containers/Fly or for LAN multi-machine setups. |

## Worker identity and enrollment

| Variable | Example | Description |
|---|---|---|

| `AGENT_OS` | `macos` \| `ubuntu` \| `debian` \| `windows` \| `ios` | OS label reported to coordinator. |
| `AGENT_MODE` | `swarm-only` \| `ide-enabled` | Whether this agent also serves IDE inference requests. |
| `AGENT_CLIENT_TYPE` | `edgecoder-native` | Runtime flavor label. Keep default unless using a custom runtime. |
| `AGENT_REGION` | unset (`FLY_REGION` when running on Fly) | Hosting region code the agent reports at registration (e.g. `sin`, `us-east-1`; lowercase letters, digits and `-`). Shown coarsely (region, country, continent) in the network's world view (`GET /network/world`); display only. |
| `AGENT_REGISTRATION_TOKEN` | _(from Nodes page)_ | Required for EDGE_RUNTIME_MODE=worker. Generated by node enrollment in the portal. The coordinator needs it whenever it does not already hold this agent's public key (first registration, after an agent or coordinator restart). Without it, a re-registration is accepted only when signed by the key the coordinator already holds. |

## Coordinator configuration

| Variable | Example | Description |
|---|---|---|
| `COORDINATOR_URL` | `https://coordinator.edgecoder.io` | URL of the coordinator this agent connects to. |
| `COORDINATOR_REGISTRATION_TOKEN` | _(from Nodes page)_ | Required for EDGE_RUNTIME_MODE=coordinator. |
| `COORDINATOR_PUBLIC_URL` | `https://coordinator.edgecoder.io` | Coordinator's publicly-reachable URL (used by coordinator itself). |
| `COORDINATOR_DISCOVERY_URL` | `$CONTROL_PLANE_URL/network/coordinators` | Control-plane endpoint for coordinator autodiscovery. |
| `COORDINATOR_DISCOVERY_URLS` | `https://edgecoder-seed-eu.fly.dev` | Portal: comma-separated coordinator URLs, tried in order. The first healthy one (`/health/runtime`) is cached for 60 s. Takes precedence over `COORDINATOR_DISCOVERY_URL` (#35). Chats go to the first listed coordinator that reports capacity, not just the first healthy one (#39). |
| `PORTAL_CHAT_CAPACITY_TIMEOUT_MS` | `2000` | Portal: how long a chat waits for a coordinator to say whether it can serve it (`/health/runtime` for the default chat, `/inference/models` for a chosen network model). No answer in time counts as no capacity. Clamped to 100..30000 (#39). |
| `PORTAL_CHAT_CAPACITY_TTL_MS` | `15000` | Portal: how long a coordinator's capacity answer is reused, so most chats start without asking. `0` asks on every chat. A "no" older than 3 s is asked again before a chat is refused with "No compute is available right now". Clamped to 0..600000 (#39). |
| `PORTAL_NONSTREAM_KEEPALIVE_AFTER_MS` | `20000` | Portal, hosted `/v1` endpoint: a non-streamed call (`stream: false`) still running after this many ms commits `200 application/json` and sends a space every `PORTAL_NONSTREAM_KEEPALIVE_MS` until the reply is ready, so Cloudflare's 100 s first-byte limit (a 524) does not cut it. JSON allows leading whitespace, so clients parse the body as usual. A call that fails after that point cannot change the status: the body is the API's error object (OpenAI `{"error":{"message","type","code"}}`, Anthropic `{"type":"error","error":{"type","message"}}`) with status 200, and no Retry-After. Before it, errors keep their status (e.g. 503 + Retry-After). `0` turns it off. Clamped to 0..600000. |
| `PORTAL_NONSTREAM_KEEPALIVE_MS` | `15000` | Portal: interval between keepalive spaces for a committed non-streamed call (see above). Clamped to 1000..90000. |
| `PORTAL_COORD_LATENCY_ROUTING` | `on` | Portal: latency-aware coordinator choice for network calls (portal chat, hosted `/v1`). `on`: the load rule's pick (most free model slots) is replaced by a coordinator that is faster by the margin and has a free slot, or by any faster one when the pick has no free slot (overflow). Expected latency = the portal's measured round trip to the coordinator + queueing (0 when a slot for the model is free; else its pickup p90 + queued rounds × call p50) + its round trip to agents holding the model. With the buyer's region known, the coordinator with the free host nearest the buyer is kept unless another with a free slot is faster end to end by the margin. End to end scores each coordinator by the free host it would place the call on (the one nearest the buyer, from `/inference/models` `freeHosts`): the portal's round trip to the coordinator + that host's round trip to the buyer (from the distance between their regions) + that host's own time for a reference call of the model (its measured speed). Calls the portal sent that a coordinator's load report does not show yet are counted against its free slots, each on the host nearest its own buyer. `off`: the load rule alone (the choice is still recorded on the routing decision). |
| `PORTAL_COORD_LATENCY_MARGIN_MS` | `30` | Portal: a latency-aware switch must save more than this many ms of expected latency. Clamped to 0..10000. |
| `PORTAL_COORD_LOCALITY_MARGIN_KM` | `700` | Portal: with the buyer's region known, a coordinator whose nearest host with a free slot is closer to the buyer than the load pick's by more than this many km takes the call (rule `locality`). `0` turns it off. Clamped to 0..20000. |
| `PORTAL_COORD_SPEED_FRESH_MS` | `300000` | Portal: two free hosts of one compute class compare by speed only when both speeds are the hosts' own measurements, at least 1.5× apart, and at most this many ms old (the coordinator's `speedAgeMs` plus the load report's age); otherwise they count as equally fast and distance to the buyer decides. A host whose coordinator does not report the age is not fresh. `0`: same-class hosts always count as equally fast. Clamped to 0..3600000. |
| `PORTAL_COORD_LATENCY_MARGIN_PCT` | `15` | Portal: ... and more than this percentage of the load pick's expected latency. Clamped to 0..100. |
| `PORTAL_MAX_AGENTS_PER_ACCOUNT` | `25` | Portal: agents one account may enrol. A new agent enrolment beyond it answers 429 `agent_limit_reached`; re-enrolling a node the account already owns is never refused. Bounds sybil identities, since every per-agent limit on the coordinator scales with them. |
| `COORDINATOR_BOOTSTRAP_URLS` | `https://coordinator.edgecoder.io` | Comma-separated fallback list. |
| `COORDINATOR_HTTP_TIMEOUT_MS` | `15000` | HTTP timeout for coordinator API calls (ms). |
| `COORDINATOR_POST_RETRIES` | `2` | Retry count for coordinator POST requests on transient failure. |
| `COORDINATOR_TRUST_PROXY` | `10.0.0.5` | Coordinator: comma-separated addresses of reverse proxies in front of it. Only a request whose TCP peer is one of these has `X-Forwarded-For` / `X-Real-IP` / `CF-Connecting-IP` / `True-Client-IP` read, and only for the displayed and geolocated client IP. Unset (default): those headers are ignored. On Fly (`FLY_APP_NAME` set by the runtime) only `Fly-Client-IP` is read. No header ever makes a request count as loopback: the embedded worker's tokenless self-registration is decided from the socket address, and a socket address listed here is never treated as loopback, so list a same-host TLS proxy here. |

## Web tool (coordinator)

Web search in chats (automatic, **Web: Auto**) and a bot's **Search the web** permission ([web tool](https://github.com/codyrs82/Edgecoder/blob/main/docs/web-tool.md)): `web_search` and `read_page` run on the coordinator (`POST /v1/tools/web/search`, `/read`, `/status`), never on a host's machine, and are billed to the caller's account per call.

| Variable | Purpose |
|---|---|
| `BRAVE_SEARCH_API_KEY` | Secret. The Brave Search API subscription token. Unset (the default): the web tool is off everywhere ("Web search isn't set up yet") and the apps hide their Web indicator. Set it with `fly secrets set BRAVE_SEARCH_API_KEY=… -a <coordinator app>` on each coordinator; it never leaves the coordinator. |
| `WEB_SEARCH_CSATS` | cSats charged per search (number ≥ 0, default `0.5`). Debited before the call (ledger reason `tool:web_search`), refunded when it fails. |
| `WEB_READ_CSATS` | cSats charged per page read (number ≥ 0, default `0.2`; reason `tool:read_page`). |
| `WEB_SEARCH_PER_HOUR` | Searches per account per hour on one coordinator (default `60`). |
| `WEB_READ_PER_HOUR` | Page reads per account per hour on one coordinator (default `120`). |
| `WEB_FREE_OWN_MACHINE_SEARCHES_PER_DAY` | Free searches per account per UTC day on one coordinator for a chat whose model runs on the account's **own machine** (the desktop's local model, or compute "My machines" / Auto on your own machine), integer 0 to 100000, default `100`. Free calls need no cSats and move none; they still count toward `WEB_SEARCH_PER_HOUR`. Past the cap a search is paid as usual (`WEB_SEARCH_CSATS`, or `needs_csats` with no balance). |
| `WEB_FREE_OWN_MACHINE_READS_PER_DAY` | Free page reads per account per UTC day for own-machine chats (integer 0 to 100000, default `200`); past it reads are paid (`WEB_READ_CSATS`). |
| `WEB_FREE_GLOBAL_PER_DAY` | Free web calls (searches and page reads, all accounts) per UTC day on one coordinator, a cost circuit-breaker (integer 0 to 10000000, default `5000`; `0` turns free web off). Past it own-machine calls are paid as usual. |
| `WEB_MAX_SEARCHES_PER_REPLY` | Desktop IDE server and portal (not the coordinator). Searches one chat reply or bot run may make (integer 0 to 50, default `3`); past it the call is refused before it costs anything. |
| `WEB_MAX_READS_PER_REPLY` | Desktop IDE server and portal (not the coordinator). Page reads one chat reply or bot run may make (integer 0 to 50, default `4`). |

## Mesh auth and security

| Variable | Description |
|---|---|
| `MESH_AUTH_TOKEN` | Shared mesh auth secret. Auto-provisioned by coordinator on successful registration if left blank. |
| `COORDINATOR_MESH_TOKEN` | Alias for `MESH_AUTH_TOKEN`. Keep aligned if both are set. |
| `MESH_PEER_ALLOWLIST` | #52: comma-separated `peerId:fingerprint@https://peer-url` entries for the peer coordinators this coordinator trusts. `@url` pins the peer's endpoint, and gossip never changes it. **In production every entry must have `@url`, or the coordinator refuses to start.** `fingerprint` is the SHA-256 (hex) of the peer's SPKI public key. With the mesh token, a peer must also be on this list and sign its registration with that key. Results it forwards must be signed too. **Required in production**: without it, token-only peer registration and forwarded results are rejected. In dev an empty list keeps the old token-only behaviour. |
| `COORDINATOR_PRIVATE_KEY_PEM` | Ed25519 private key (PKCS#8 PEM) for this coordinator's mesh identity. Set it on every coordinator that peers, since a generated key changes on each restart and would drop off its peers' allowlists. Fingerprint for `MESH_PEER_ALLOWLIST`: `node -e 'const c=require("crypto");const k=c.createPublicKey(process.env.COORDINATOR_PRIVATE_KEY_PEM);console.log(c.createHash("sha256").update(k.export({type:"spki",format:"der"})).digest("hex"))'` |
| `INFERENCE_AUTH_TOKEN` | Auth token for the inference service API. |
| `ADMIN_API_TOKEN` | Admin token for control-plane operator APIs. On a coordinator it is also the only credential for operator routes: treasury policies, issuance votes and recalculation, price propose/consensus, payment intents for a named account, payment reconcile and forced model rollouts (`/orchestration/*/ollama-install`). The mesh token alone is refused there (sent as `x-admin-token`). On a coordinator these routes also refuse requests from outside (see `ADMIN_ALLOWED_CIDRS`): call them from the machine (`fly ssh console`, 127.0.0.1) or over Fly's private network. |
| `PORTAL_SERVICE_TOKEN` | Internal service token for portal ↔ coordinator/control-plane calls. On the control plane it stands in for the admin token on reads (GET) only. |
| `ADMIN_ALLOWED_CIDRS` | Coordinator. Comma list of extra CIDRs whose **socket** address may use admin-token routes (`/admin/*` and every other route that takes `x-admin-token`). Unset: loopback, plus Fly's private network `fdaa::/16` on Fly (`FLY_APP_NAME` set), or the private ranges (RFC 1918, `fc00::/7`, `fe80::/10`) elsewhere. A request carrying `Fly-Client-IP` or `Fly-Forwarded-Port` (Fly's public edge sets them) is refused, as is one from a `COORDINATOR_TRUST_PROXY` address. Headers never grant access. Refusals are `403 admin_internal_only`; the token is still required. |
| `ADMIN_LISTEN_PORT` | Coordinator, default `0` (off). Also serve the coordinator on this port, bound to `ADMIN_LISTEN_HOST`, for operator calls over Fly's private network (the public port is IPv4 only, which 6PN cannot reach). Keep it out of every `fly.toml` service so only the private network reaches it; the portal's `COORDINATOR_ADMIN_URLS` point at it. |
| `ADMIN_LISTEN_HOST` | Coordinator, default `::` (IPv6 and IPv4). Bind address for `ADMIN_LISTEN_PORT`. |
| `COORDINATOR_ADMIN_URLS` | Portal, optional. Comma list of coordinator URLs for admin-token calls (Settings > Revenue, Network, Alerts, node dismiss/remove), e.g. `http://edgecoder-seed.internal:4311`. Coordinators refuse admin calls that come through the public edge, so set this in production. Unset: the discovered coordinator URLs. |
| `PORTAL_ACTION_SIGNING_KEY` | Portal, secret. Ed25519 private key (PKCS#8 PEM, or the 32-byte seed as base64 or hex). The portal signs every withdrawal and payout-destination request it sends a coordinator for a logged-in user with it: the account, the action, a hash of the invoice or destination, a one-time nonce and an expiry of at most 2 minutes (`x-portal-action`). Generating and rotating it: `docs/security/rotation.md`. |

## Result verification (#50, #105, #106, #117, #162)

Reputation, abandonment and replica exclusion are keyed on the agent's reward account (its agent id only when it has none), so a new agent id doesn't reset them. With Postgres, per-account reputation (`verification_reputation`) and held results (`pending_verifications`) are stored: a restart holds them again with their original deadline and re-issues the replica, and both seeds share one reputation per account. A result outvoted by an agreeing majority is a strike for the automatic blacklister (3 within an hour blacklist the agent id).

| Variable | Default | Description |
|---|---|---|
| `RESULT_VERIFICATION_RATE` | `0` | Base fraction of subtasks re-executed for verification. `0` = verification off (the default). |
| `RESULT_VERIFICATION_ABANDON_PENALTY` | `0.25` | Reputation lost for claiming a verification replica and never reporting it. |
| `RESULT_VERIFICATION_REPLICA_CLAIM_TIMEOUT_MS` | `300000` | A claimed replica with no report after this long is penalized and reassigned to an agent on a reward account that hasn't run or abandoned it. This repeats for each new stall while more than this long remains before the overall timeout (`RESULT_VERIFICATION_TIMEOUT_MS`, counted from the original result; reassignment doesn't extend it). When no eligible agent is left the replica stays unclaimed and the subtask settles at the timeout. |
| `RESULT_VERIFICATION_MAX_REASSIGNMENTS` | unlimited | Optional hard cap (0–1000) on reassignments per sampled subtask. Unset: bounded by the overall timeout as above. |
| `RESULT_VERIFICATION_REPUTATION_CACHE_MAX` | `50000` | Most reputations kept in memory. Entries at or above the initial reputation are dropped first, so eviction never raises a penalized account's trust. With Postgres the stored value is reloaded on the account's next result. |
| `RESULT_VERIFICATION_INITIAL_REPUTATION` | `0.5` | Reputation (0–1) of a reward account the coordinator has never seen. Below 1 so a caught agent can't regain full trust by re-registering; lower reputation means its results are re-executed more often. |
| `RESULT_VERIFICATION_MAX_EXECUTIONS` | `3` | Max executions of a sampled subtask (original + replicas), 2–3. Values above 3 are capped. At most this minus one replicas run per sampled subtask; whether winning replicas are paid is set by `RESULT_VERIFICATION_MINT_REPLICA_REWARDS`. |
| `RESULT_VERIFICATION_MINT_REPLICA_REWARDS` | `false` | Pay winning verification replicas from newly minted compute credits (`true`/`1`/`yes` to enable). Off by default: only the original execution is paid, so verification doesn't add to the credit supply. **Enabling minting requires Cody's approval.** The coordinator logs a startup warning whenever `RESULT_VERIFICATION_RATE` is above 0, saying whether replicas are paid. |

## Coordinator: best-fit routing (model `auto`)

A request with `model: "auto"` is routed by the coordinator: it describes the job (type, complexity 0 to 1, tools, context, reply length; hints in the request's `edgecoder` object or `x-edgecoder-*` headers), scores every model and class available now on quality, latency, price and reliability, and prefers the best agent for a moment. The formula is described in `src/swarm/coordinator/best-fit.ts`; Settings > Network shows recent decisions. A value outside the reader's range uses the default.

| Variable | Default | Description |
|---|---|---|
| `BEST_FIT_W_QUALITY` | `0.4` | Base weight of capability fit (model size against what the job needs, coder bonus, right-sizing). 0 to 10; the four weights are normalised. |
| `BEST_FIT_W_LATENCY` | `0.3` | Base weight of expected time (wait for a slot, RTT, prefill and decode from measured tok/s). |
| `BEST_FIT_W_PRICE` | `0.15` | Base weight of the estimated cost (token price by size, never below the class power floor). |
| `BEST_FIT_W_RELIABILITY` | `0.15` | Base weight of reliability (verifier score, verification, recent failures). |

## Production alerting (portal and coordinator)

The portal and every coordinator watch the network and tell the owner when something breaks (`src/alerting`). Each alert has a title, what is wrong, since when, who saw it and a link to Settings > Network, where the **Alerts** card lists active alerts and history, has an **Acknowledge** button per alert (no more reminders until it resolves) and **Send test alert**. A resolution notice follows when the alert clears. One incident per alert key; at most one notification per key per `ALERT_RATE_LIMIT_MINUTES`, also across a flapping key; a quiet reminder every `ALERT_RENOTIFY_MINUTES` while active and unacknowledged. State is kept in Postgres (`ops_alerts`, `ops_alert_events`, `ops_alert_state`, created on first use), in memory while the database is down. Payout and ledger alerts are shared by the coordinators on one database, so they notify once.

What is watched: the portal watches every coordinator's `/health/runtime`, network capacity (a model with at least `ALERT_POPULAR_MODEL_MIN_CALLS_24H` requests and no agent online for `ALERT_CAPACITY_GAP_MINUTES`, a host at critical memory pressure for 5 minutes, a no-capacity spike), its database and the backup reports. Each coordinator watches its mesh peers' `/health/runtime` and the portal's `/health` (a service that is down cannot report itself), its Lightning node (unreachable, not synced to chain or graph for 10 minutes, low outbound liquidity in active channels, low inbound capacity (checked every `ALERT_LN_INBOUND_CHECK_MINUTES`), channels inactive for 10 minutes), payouts (any failure in the last hour, more than `ALERT_PAYOUT_FAILURES_PER_HOUR`, Lightning payouts pending longer than `ALERT_PAYOUT_PENDING_MINUTES`, the payout kill switch), purchase invoice creation failures, the periodic ledger reconciliation and its own ordering chain, its Postgres pool errors, and security events (integrity events such as `ledger_chain_break` at once; `bot_control_not_owner`, `code_control_not_owner`, `model_control_not_owner` at once; repeated `failed_auth`, `invalid_signature`, `replay_attempt`; an auto-blacklist of a host with an enrolled owner or verified hardware at once, other auto-blacklists from 5 an hour).

### Backup check

A coordinator cannot list Fly Postgres backups, so a scheduled job does: `scripts/ops/report-pg-backups.sh` runs `fly postgres backup list` for each app in `PG_APPS` and posts the newest successful backup time to the portal's `POST /internal/alerts/backup-report` (portal service token). Run it every few hours (GitHub Actions schedule, cron on an ops machine or a Fly scheduled machine) with `PORTAL_URL`, `PORTAL_SERVICE_TOKEN`, `PG_APPS` and `FLY_API_TOKEN`; `DRY_RUN=1` prints the reports instead. A failed listing is reported as "no successful backup known", which alerts. Set `ALERT_BACKUP_EXPECTED=1` on the portal once the job is scheduled.

## Brand-account posting (portal)

Settings > Social posts (system admins) holds the brand account's post queue (`src/social`, `src/portal/social.ts`). A job on the portal drafts posts from live data: a weekly network report (hosts online, jobs run and sats paid to hosts over 7 days, from the Network admin view and the coordinator's revenue report), new desktop and agent releases (the GitHub releases listing), and new pages in the docs sitemap; iOS release notes and anything else are written in the page's compose box or loaded through the admin bulk import (`POST /portal/api/admin/social/import`, drafts only). Every post needs an admin's approval; approving sends it at once (or at the next run), unless it has a send time (shown and edited in America/Chicago time), in which case it waits until then (checked every minute). A post can carry up to 4 images (PNG or JPEG, 5 MB each, optional alt text; stored in Postgres and uploaded with `POST /2/media/upload`). Posts can be grouped into a thread: approving one approves the whole thread, and each next post replies only to the previous post of the same thread, which the portal itself just posted; a failure stops the thread and marks the rest failed. Posts go to X (`POST /2/tweets`, OAuth 1.0a user context) and are cross-posted to Nostr (threads as plain sequential notes). Rules are enforced in code: original posts only (no @mentions, replies to anyone else, or reposts), 280 characters with links counting 23, no text posted in the last 90 days, and the never-claim list (no "open source", end-to-end encryption, private network or compute, passive or guaranteed income, frontier-model parity; nothing about earning, hosting or withdrawing next to the iOS app). A draft that breaks a rule cannot be approved until it is edited. Two switches must both be on before anything is sent: the page's **Posting** switch (stored; starts paused, which also stops drafting) and `SOCIAL_POSTING_ENABLED=1`. State is kept in Postgres (`social_posts`, `social_post_images`, `social_state`, created on first use).

## Growth signals (portal)

The portal counts visits from tagged links and tells the owner about new sign-ups (`src/growth`, `src/portal/growth.ts`). A GET of a public HTML page with `utm_source` / `utm_medium` / `utm_campaign` / `utm_content` tags, or the `/x/<campaign>` short link, adds one visit to a daily aggregate per America/Chicago day and campaign (`growth_utm_daily`; no IP, user agent or account is stored for a visit). Robots (by user agent) and `HEAD` requests are not counted, and a visitor counts at most once per campaign per day: a first-party cookie, `ec_utm` (`__Host-ec_utm` when cookies are Secure; HttpOnly, SameSite=Lax), remembers the campaigns already counted today and the first campaign that brought the visitor, for 30 days. A new human account (email and password, Google, Microsoft or GitHub; never an agent account) is credited to that first-touch campaign (`growth_signups`, counted as a sign-up for the campaign) and emailed to `ALERT_EMAILS` through Resend (see Alerting) with its address, sign-up method, time, campaign and a link to Settings > Admin. At most 10 single alerts go out per hour; more are held and sent together as one message. Alerts never delay or fail a sign-up. Every day at 8:00 America/Chicago the portal emails `ALERT_EMAILS` a digest of the previous day: visits and sign-ups by campaign and the new sign-ups (one line when there were none). Settings > Social posts shows the last 14 days under **Traffic from X**, each campaign linked to the post whose text carries its `/x/<campaign>` link. Ads use full links with `utm_source=x&utm_medium=paid&utm_campaign=<name>&utm_content=<creative>`. Tables are created on first use (`growth_utm_daily`, `growth_signups`, `growth_state`).

| Variable | Default | Description |
|---|---|---|
| `SIGNUP_ALERT_IGNORE` | unset | Comma-separated sign-ups that never alert and are left out of the campaign sign-up counts and the digest's list (the owner's own and test accounts): exact addresses (`me@example.com`), whole domains (`@example.com`) or `*` globs (`cody+*@example.com`). Case-insensitive. |

## Startup validation (#15)

Each service reads its environment once at startup through a zod schema. An invalid value (for example `abc` for a port or an interval, `maybe` for a flag, or a URL without `http(s)://`) stops the service with exit code 1. The error names each variable and what is wrong with it, and lists every problem at once. The value of a secret (a variable whose name contains `TOKEN`, `SECRET`, `PASSWORD`, `PRIVATE_KEY`, `API_KEY` and the like) is never printed. Empty values count as unset, and variables no schema lists are ignored.

The schemas are collected in `src/config/index.ts`. `tests/common/env-docs.test.ts` fails when the tables on this page and the schemas list different variable names, and when code in `src/` reads a variable no schema declares.

| Service | Schema | Production-only rules |
|---|---|---|
| inference | `src/inference/config.ts` | `INFERENCE_AUTH_TOKEN` at least 32 characters |
| portal | `src/portal/config.ts` | `PORTAL_SERVICE_TOKEN`, `RESEND_API_KEY`, `DOCS_SITE_URL` required; `CONTROL_PLANE_URL` or `COORDINATOR_DISCOVERY_URLS`; `CONTROL_PLANE_ADMIN_TOKEN` when `CONTROL_PLANE_URL` is set; https for `PORTAL_PUBLIC_URL`, `DOCS_SITE_URL` and passkey origins |
| coordinator | `src/swarm/coordinator-config.ts` | unchanged (`requireProdEnv`) |
| control-plane | `src/control-plane/config.ts` | `ADMIN_API_TOKEN` required in every environment; at least 32 characters when `NODE_ENV=production` |
| anchor proxy | `src/config/anchor-proxy.ts` | none; `ANCHOR_PROXY_TOKEN`, `BITCOIND_RPC_URL`, `BITCOIND_RPC_USER` and `BITCOIND_RPC_PASSWORD` are required in every environment |
| worker | `src/config/worker.ts` | none |
| IDE provider | `src/config/ide-provider.ts` | none |
| all-in-one entry, launcher | `src/config/all-in-one.ts` | none of its own; the services it starts apply theirs |

## Observability (#14)

| Variable | Default | Description |
|---|---|---|
| `LOG_LEVEL` | `info` | Log level for every service: `fatal`, `error`, `warn`, `info`, `debug`, `trace` or `silent`. Any other value is treated as `info`. |
| `METRICS_TOKEN` | unset | Bearer token for Prometheus `/metrics` (inference: `/metrics/prometheus`). Unset: only a caller on the same machine can read metrics, everyone else gets `404`. Set: other callers must send `authorization: Bearer <token>`, and get `401` without it. Use a long random value (for example `openssl rand -hex 32`); it is separate from the mesh and admin tokens, which are not accepted here. |
| `REQUEST_ID_FORWARD_ORIGINS` | unset | Extra comma-separated origins that receive `x-request-id` on outbound calls. The service URLs (`COORDINATOR_URL`, `CONTROL_PLANE_URL`, `INFERENCE_URL`, `PORTAL_SERVICE_URL`, `COORDINATOR_PUBLIC_URL`, `COORDINATOR_DISCOVERY_URLS`) are included automatically; third-party APIs never get it. |
| `SENTRY_DSN` | unset | Error tracking. Unset: off, the Sentry SDK is never loaded and nothing is sent. Set: 5xx errors and fatal process errors (`uncaughtException`, `unhandledRejection`) go to Sentry. |
| `SENTRY_ENVIRONMENT` | `NODE_ENV`, else `development` | Sentry environment name. |
| `SENTRY_RELEASE` | `edgecoder@<package version>` | Sentry release (for example the git SHA). |

### Logs

Every service writes one JSON object per line to stdout (pino): `level`, `time`, `service`, `msg`, plus `requestId` on every line written while a request is being handled.

- **Request id.** An incoming `x-request-id` is kept if it is 8 to 128 characters of `A-Z a-z 0-9 . _ : -`; anything else is replaced with a new UUID. The id is returned in the `x-request-id` response header and forwarded on calls to the other EdgeCoder services.
- **Redaction.** Credential headers (`authorization`, `cookie`, `set-cookie`, `x-admin-token`, `x-mesh-token`, `x-inference-token`, `x-portal-service-token`, `x-api-key`, the request-signature headers) and any field whose name looks secret (`password`, `token`, `secret`, `mnemonic`, `seed`, `preimage`, `apiKey`, `privateKey`, ...) are written as `[redacted]`, at any depth. Credentials inside strings (`//user:pass@host`, `Bearer <token>`) are masked too.
- **Request bodies and headers are not logged.** A request line carries the method, the URL with secret query values masked, the host and the peer address.

### Metrics

`/metrics` (inference: `/metrics/prometheus`, because that service already has a JSON `/metrics`) serves the Prometheus text format:

| Metric | Labels | From |
|---|---|---|
| `edgecoder_http_requests_total` | `service`, `method`, `route`, `status_class` | every service |
| `edgecoder_http_request_duration_seconds` (histogram) | `service`, `method`, `route`, `status_class` | every service |
| `process_*`, `nodejs_*` | none | every service (CPU, memory, event loop lag, GC, open handles) |
| `edgecoder_queue_depth`, `edgecoder_queue_results` | `service` | coordinator |
| `edgecoder_connected_agents` | `service` | coordinator |
| `edgecoder_dispatch_pickup_p50_ms`, `edgecoder_dispatch_pickup_p90_ms`, `edgecoder_dispatch_nudges_sent` | `service` | coordinator: time from a subtask becoming claimable to an agent claiming it (last 1000 claims), and `work_available` nudges sent |
| `edgecoder_payout_reconcile_status` | `service`, `status` (`ok`, `alert`, `tripped`, `error`, `unsupported`, `never_run`; 1 for the current one) | coordinator |
| `edgecoder_payout_reconcile_last_run_timestamp_seconds` | `service` | coordinator |
| `edgecoder_anchor_proxy_bitcoind_reachable`, `edgecoder_anchor_proxy_block_height`, `edgecoder_anchor_proxy_last_health_check_timestamp_seconds` | `service` | anchor proxy (updated by its health check) |

`route` is the route pattern (`/nodes/:nodeId`), never the URL, and `status_class` is `2xx`..`5xx`, so no ids, tokens or user data reach a label. Requests that match no route are counted as `route="unmatched"`.

**Access.** The services are reachable from the internet, so `/metrics` is never public. A request counts as local only when it connects from a loopback address, carries no proxy headers (`x-forwarded-for`, `cf-connecting-ip`, `fly-client-ip`, `via`, ...) and uses a loopback `Host`. If you run your own reverse proxy on the same machine, make sure it sets `x-forwarded-for` (Caddy and cloudflared do by default; nginx needs `proxy_set_header X-Forwarded-For`), or it will be treated as a local caller. On the portal, `/metrics` is exempt from the origin lock so a scraper can reach the machine directly; the rule above still applies. The IDE provider (port 4304) additionally requires its own bearer token on every path.

### Error tracking

With `SENTRY_DSN` set, each event carries the error (type, message, stack), the tags `service`, `requestId`, `route` (the pattern) and `method`, the release, the environment and the machine's hostname. Nothing else about the request is attached, and every event is scrubbed before it is sent: no request body, no cookies or headers, no query strings, and credentials quoted in an error message are masked. Only errors answered with a 5xx are reported; 4xx are not. After a fatal process error the service still exits with code 1, once the report has been sent or two seconds have passed.

### Alerting on 5xx without Sentry

Example Prometheus rules:

```yaml
groups:
  - name: edgecoder-http
    rules:
      - alert: EdgeCoderHigh5xxRate
        # more than 5% of requests failing with 5xx for 10 minutes, per service
        expr: |
          sum by (service) (rate(edgecoder_http_requests_total{status_class="5xx"}[5m]))
            / sum by (service) (rate(edgecoder_http_requests_total[5m])) > 0.05
        for: 10m
        labels: { severity: page }
      - alert: EdgeCoder5xxOnRoute
        # any single route returning 5xx steadily (catches a broken endpoint on a busy service)
        expr: sum by (service, route) (rate(edgecoder_http_requests_total{status_class="5xx"}[5m])) > 0.1
        for: 15m
        labels: { severity: ticket }
      - alert: EdgeCoderPayoutReconcileNotOk
        expr: max by (service) (edgecoder_payout_reconcile_status{status=~"alert|tripped|error"}) == 1
        for: 10m
        labels: { severity: page }
      - alert: EdgeCoderMetricsMissing
        # the scrape itself failing usually means the service is down or METRICS_TOKEN is wrong
        expr: up{job=~"edgecoder-.*"} == 0
        for: 5m
        labels: { severity: page }
```

Scrape `/metrics` (inference: `/metrics/prometheus`) with `authorization: Bearer $METRICS_TOKEN`.

## Operational guidance

**Production fail-fast (#5).** With `NODE_ENV=production`, services refuse to boot when required secrets are empty (an empty token no longer means "auth off"):
- coordinator: `MESH_AUTH_TOKEN`, `PORTAL_SERVICE_URL`, `PORTAL_SERVICE_TOKEN`, `ADMIN_API_TOKEN`, `PAYMENT_WEBHOOK_SECRET`, `DATABASE_URL` (#55: replay/idempotency keys and lease state are durable only in Postgres), and `LIGHTNING_PROVIDER` unless `ECONOMY_PAYMENTS_ENABLED=false`
- portal: `PORTAL_SERVICE_TOKEN`, `RESEND_API_KEY`, `DOCS_SITE_URL` (plus the existing passkey/URL checks)
- inference: `INFERENCE_AUTH_TOKEN`
- control-plane: `ADMIN_API_TOKEN`

Run a `fly secrets list` checklist against this list before any deploy.

- Keep secrets in production secret stores (Fly Secrets, AWS SSM, etc.) rather than static env files.
- On macOS, the env file is `/etc/edgecoder/edgecoder.env` (chmod 600, owned by root).
- On Linux, same path — the systemd `EnvironmentFile=-/etc/edgecoder/edgecoder.env` directive loads it.
- Review and rotate `MESH_AUTH_TOKEN` periodically.
